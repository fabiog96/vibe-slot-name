     Betting Modal — Polymarket Style (Frontend Mock)

     Context

     Modale scommesse stile Polymarket accessibile da toggle nell'header. Mock
     frontend con logica completa: chip, quote dinamiche basate su frequenza
     storica, tipi di scommessa avanzati (singola, combo, inversa). Self-betting
      permesso. In futuro BE con sessioni multi-utente.

     Sistema di Quote (Odds)

     Le quote si basano sulla frequenza storica di uscita di ogni partecipante:

     quota = totalSpins / (timesSelected + 1)

     - Capra uscito 5/20 volte → quota ~3.3x (bassa, esce spesso)
     - Yang uscito 0/20 volte → quota ~20x (alta, non esce mai)
     - Minimo 1.1x, massimo capped a 20x

     Lo storico viene tracciato in-session (array di risultati passati). In
     futuro persistito via BE.

     Tipi di Scommessa

     ┌───────────────┬──────────────────────┬─────────────────────────────────┐
     │     Tipo      │     Descrizione      │         Calcolo payout          │
     ├───────────────┼──────────────────────┼─────────────────────────────────┤
     │ Singola       │ "X vince ruolo Y"    │ quota di X × puntata            │
     ├───────────────┼──────────────────────┼─────────────────────────────────┤
     │ Qualsiasi     │ "X vince almeno un   │ quota ridotta (quota / N_ruoli) │
     │ ruolo         │ ruolo"               │  × puntata                      │
     ├───────────────┼──────────────────────┼─────────────────────────────────┤
     │ Accoppiata    │ "X vince A e Y vince │ quota_X × quota_Y × puntata     │
     │               │  B"                  │                                 │
     ├───────────────┼──────────────────────┼─────────────────────────────────┤
     │ Non esce      │ "X non viene         │ (1 / (1 - prob_X)) × puntata    │
     │               │ estratto"            │                                 │
     └───────────────┴──────────────────────┴─────────────────────────────────┘

     Sistema Chip

     - Ogni utente parte con 100 chip
     - Puntata minima: 1 chip
     - Puntata massima: tutte le chip disponibili
     - Bancarotta (0 chip): visual "BANKRUPT!" + bet disabilitate
       - Mock: badge rosso, impossibile scommettere
       - Decisione BE futura: chi va in bancarotta si auto-assegna a un ruolo la
      settimana successiva

     UX Flow

     1. Click icona nell'header → modale overlay
     2. Scegli tipo di scommessa (tab: Singola | Combo | Inversa)
     3. Seleziona partecipante(i) e ruolo(i)
     4. Imposta puntata con slider o input
     5. Conferma bet → chip scalate
     6. Chiudi modale, fai spin
     7. Riapri modale → risultati con P&L

  odds = (total_spins + 1) / (times_selected + 1)

  Meno esci → più la tua quota sale (sei una "sorpresa", scommettere su di te
  paga tanto).

  È tipo il concetto di Polymarket: se un evento è probabile (basato sullo
  storico), il payout è basso. Se è improbabile, il payout è alto.

  Il cap [1.1, 20.0]

  - Min 1.1x: anche chi esce sempre non puo' avere quota < 1.1 (altrimenti
  scommettere non conviene mai)
  - Max 20x: evita che chi non esce mai abbia quote assurde (tipo 100x) che
  rompono l'economia chip con una singola vincita

  Il cap è arbitrario — possiamo aggiustarlo. Vuoi che lo cambiamo?

⏺ Per l'auth su progetto personale con free tier, le opzioni migliori sono:

  Firebase Auth (Google)
  - Free tier generoso: 50k MAU gratis
  - SDK JS leggero, zero backend per il login
  - Google/GitHub/email login in 5 minuti
  - JWT verificabile lato BE con firebase-admin

  Supabase Auth
  - Free tier: 50k MAU
  - Basato su GoTrue (open source)
  - Include anche un DB Postgres free (potrebbe sostituire Mongo)
  - JWT standard, facile da verificare

  Auth0
  - Free tier: 25k MAU
  - Il più "enterprise" ma anche il più pesante da configurare per un side
  project

  La mia raccomandazione: Firebase Auth. Motivi:
  - Setup più veloce in assoluto (10 minuti)
  - SDK frontend minuscolo
  - Il JWT si verifica lato FastAPI con una sola riga (firebase-admin)
  - Non aggiungi un intero platform (come Supabase) solo per l'auth
  - Perfetto per side project: zero costi, zero manutenzione

  Per il DB: MongoDB Atlas free tier (512MB) è perfetto per questo caso d'uso —
  uno spin a settimana, pochi utenti, dati leggeri.

⏺ Doc aggiornato. Per la tua domanda sulla connessione MongoDB in FastAPI:

  Connessione MongoDB in FastAPI

  Usi motor (driver async per MongoDB) + Pydantic per i modelli:

  # app/database.py
  from motor.motor_asyncio import AsyncIOMotorClient

  client: AsyncIOMotorClient | None = None
  db = None

  async def connect():
      global client, db
      client = AsyncIOMotorClient("mongodb+srv://user:pass@cluster.mongodb.net")
      db = client["vibe_slot"]

  async def disconnect():
      if client:
          client.close()

  # app/main.py
  from contextlib import asynccontextmanager
  from fastapi import FastAPI

  @asynccontextmanager
  async def lifespan(app: FastAPI):
      await connect()    # startup
      yield
      await disconnect() # shutdown

  app = FastAPI(lifespan=lifespan)

  # nei service, esempio:
  from app.database import db

  async def get_user(uid: str):
      return await db["users"].find_one({"_id": uid})

  async def deduct_chips(uid: str, amount: int) -> bool:
      result = await db["users"].find_one_and_update(
          {"_id": uid, "chips": {"$gte": amount}},
          {"$inc": {"chips": -amount}},
      )
      return result is not None  # False = chip insufficienti

  Dipendenze: motor, pymongo (installato automaticamente con motor). Niente ORM
  pesante — Pydantic per validazione, motor per le query. Pulito e leggero.

❯ API Gateway │ 1M req/mese (12 mesi) invece?                                   

⏺ Hai ragione a notarlo. API Gateway REST ha il free tier solo per i primi 12 
  mesi di AWS. Dopo costa $3.50 per milione di request.

  Per il tuo caso (~34k req/mese) sarebbero circa $0.12/mese dopo il primo anno
  — niente di preoccupante.

  Ma c'e' un'alternativa: API Gateway HTTP API (non REST API). Costa $1.00 per 
  milione invece di $3.50, e per il tuo volume sarebbe ~$0.03/mese. Fa tutto
  quello che ti serve.

  Oppure puoi usare un Function URL di Lambda — endpoint HTTP diretto senza API
  Gateway, completamente gratis per sempre. Il limite è che hai meno controlli
  (no rate limiting, no custom domain nativo), ma per un side project con 11-20
  utenti va benissimo.

  Quale preferisci?

❯ Lambda function url non le conosco cosa sono?                                 

⏺ È una feature di Lambda che ti dà un endpoint HTTPS diretto sulla Lambda,
  senza passare da API Gateway. In pratica:

  Con API Gateway (classico)

  Client → API Gateway → Lambda
  Paghi API Gateway + Lambda.

  Con Function URL

  Client → Lambda (direttamente)
  Paghi solo Lambda. L'URL è tipo:
  https://abc123xyz.lambda-url.eu-west-1.on.aws/

  Cosa supporta

  - HTTPS automatico (SSL incluso)
  - CORS configurabile
  - Auth via IAM o nessuna (pubblica) — nel tuo caso l'auth la gestisci tu con
  Cognito JWT dentro FastAPI
  - Supporta Mangum normalmente — FastAPI funziona identico

  Cosa NON ha rispetto ad API Gateway

  ┌────────────────────────────────┬──────────────────────────┬────────────┐
  │            Feature             │       Function URL       │    API     │
  │                                │                          │  Gateway   │
  ├────────────────────────────────┼──────────────────────────┼────────────┤
  │ Custom domain                  │ No (serve CloudFront     │ Si         │
  │ (api.tuodominio.com)           │ davanti)                 │            │
  ├────────────────────────────────┼──────────────────────────┼────────────┤
  │ Rate limiting                  │ No                       │ Si         │
  ├────────────────────────────────┼──────────────────────────┼────────────┤
  │ API keys                       │ No                       │ Si         │
  ├────────────────────────────────┼──────────────────────────┼────────────┤
  │ WAF (firewall)                 │ No                       │ Si         │
  ├────────────────────────────────┼──────────────────────────┼────────────┤
  │ Caching                        │ No                       │ Si         │
  └────────────────────────────────┴──────────────────────────┴────────────┘

  Per il tuo caso

  Con 11-20 utenti fidati, non ti servono rate limiting, API keys, o WAF. L'URL
  autogenerato da AWS è brutto ma funziona. Se un domani vuoi un dominio custom,
   aggiungi CloudFront davanti (ha anche lui un free tier generoso).

  In sintesi: stessa roba, gratis per sempre, zero config in più. L'unico
  trade-off è l'URL brutto.

❯ per la parte di FE stavo pensando o S3 + cluodfront o Cloudflare              

⏺ Entrambe ottime opzioni:

  S3 + CloudFront

  - Tutto AWS, stesso ecosistema
  - S3 free tier: 5GB + 20k GET/mese (12 mesi), poi ~$0.02/mese
  - CloudFront: 1TB + 10M req/mese (per sempre)
  - Custom domain + SSL via ACM (gratis)
  - Puoi usare lo stesso CloudFront sia per FE (S3) che per BE (Lambda Function
  URL) — unico dominio

  Cloudflare Pages

  - Gratis per sempre, senza limiti pratici
  - Build + deploy da GitHub automatico (come GitHub Pages ma meglio)
  - CDN globale inclusa
  - Custom domain + SSL gratis
  - Velocissimo, zero config

  Il confronto

  ┌──────────────────────┬────────────────────────────┬────────────────────┐
  │                      │      S3 + CloudFront       │  Cloudflare Pages  │
  ├──────────────────────┼────────────────────────────┼────────────────────┤
  │ Costo                │ ~zero                      │ Zero               │
  ├──────────────────────┼────────────────────────────┼────────────────────┤
  │ Deploy               │ Manuale (S3 sync) o CI/CD  │ Git push → live    │
  ├──────────────────────┼────────────────────────────┼────────────────────┤
  │ Ecosistema           │ Tutto AWS                  │ Servizio esterno   │
  ├──────────────────────┼────────────────────────────┼────────────────────┤
  │ Custom domain        │ Si (ACM)                   │ Si (piu' semplice) │
  ├──────────────────────┼────────────────────────────┼────────────────────┤
  │ FE + BE stesso       │ Si (un CloudFront, 2       │ No (BE resta su    │
  │ dominio              │ origins)                   │ AWS)               │
  └──────────────────────┴────────────────────────────┴────────────────────┘

  La mia raccomandazione

  S3 + CloudFront — perché puoi mettere FE e BE sotto lo stesso dominio con un
  unico CloudFront:

  tuodominio.com          → S3 (React app)
  tuodominio.com/api/*    → Lambda Function URL (FastAPI)

  Niente problemi di CORS, tutto pulito, tutto AWS. Cloudflare Pages è ottimo ma
   poi hai FE su Cloudflare e BE su AWS con domini diversi — devi gestire CORS.

  Cosa preferisci?
